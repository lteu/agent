终端 LLM Agent 的 8 次试用、注册与充值

Agent 运行在用户终端，但 LLM Key 只存在你的服务器。CLI 通过 HTTPS 调用你的中转 API； 服务端负责匿名试用、账户、余额、扣费和真正的 LLM 调用。

直接结论

正确的 PoC 形态

  • 用户安装 CLI，CLI 内没有 LLM Key。
  • 首次运行向服务器领取匿名 installation_token。
  • 前 8 个 Agent run 由服务器原子计数。
  • 第 9 个 run 被服务器拒绝，CLI 提示执行 agent login。
  • 注册后执行 agent billing，打开一次性充值链接。
  • 支付 Webhook 确认后，CLI 轮询/刷新余额并继续工作。

不要这样做

  • 把 LLM Key 编译进 CLI
  • 在本地文件记录“已用 8 次”
  • 相信 CLI 上报的余额、价格或用户 ID
  • 用一个长期固定 API Key 给所有 CLI
  • 支付成功页一打开就给账户加钱
CLI 是公开客户端，不可能藏住 Secret 用户拥有二进制、进程内存、配置目录和网络环境。混淆、打包或把 Key 拆成几段都只能拖延提取， 不能保护 LLM Key。唯一可靠边界是：真实 Key 从不离开你的服务器。

终端 Agent 架构

用户终端 / CLI
  • Agent loop 与终端 UI
  • 读取项目文件、执行本地工具
  • 保存匿名令牌或登录 token
  • 调用你的 HTTPS API
→
你的 Gateway API
  • 验证 installation/access token
  • 检查 8 次试用或付费余额
  • 控制模型、最大 token 与成本
  • 注入 LLM Key，转发/流式返回
  • 记录用量、账本和审计事件
→
外部服务
  • LLM Provider
  • 支付 Checkout / Webhook
  • 邮件或 OAuth 登录
  • PoC 数据库：SQLite
本地工具仍在本地执行 如果 Agent 要读文件、改代码或运行 shell，服务器不必拿到整个项目。推荐协议是： CLI 把必要的上下文发给 Gateway，Gateway 调 LLM；模型返回工具调用意图，CLI 在本地确认并执行， 再把结构化结果发回。服务端只控制模型访问与计费。

8 次试用怎样计数

首次启动

CLI 生成本地密钥对或随机安装 ID，调用 POST /v1/installations。服务器创建匿名安装记录，返回高熵 token。

每次 Agent run

CLI 发送唯一 request_id。服务器在 SQLite 事务内处理幂等并将 used_runs 从 0 原子增加到 8。

第 9 次

Gateway 不调用 LLM，返回 TRIAL_EXHAUSTED。CLI 输出剩余为 0，并给出登录及充值命令。

“同一个人只能 8 次”无法在匿名 CLI 上被严格保证 用户可以删除 ~/.your-agent、重装 CLI、修改开源代码、换机器或换 IP。 服务端安装令牌只能防止普通用户无意重置，不能等同真实身份。
PoC 策略建议代价
安装令牌随机 token 只保存本地；服务端只存哈希。重装会得到新身份。体验最好，最易被重置。
粗粒度风控同 IP/网段创建安装数、每小时 run 数、并发数设上限；异常时验证码。共享网络可能误伤，规则要宽松。
机器信号只作为风险信号，不作为唯一身份；做 HMAC 后短期保存。有隐私和跨平台兼容问题。
强试用约束第一次使用就要求邮箱/GitHub 登录，把 8 次绑定账户。最可靠，但安装后的首次体验更差。

建议 PoC 先用“安装令牌 + IP 速率限制 + 每日总成本上限”，验证转化后再决定是否把试用前置到登录。

终端中的注册与登录

方案 A：Device Code（最适合 SSH）

  1. CLI 请求 device_code、短 user_code 和验证 URL。
  2. 用户在任意浏览器登录/注册并输入短码。
  3. CLI 按服务端给定间隔轮询，直到批准、拒绝或过期。
  4. 服务端向 CLI 签发短期 access token 与可轮换 refresh token。

方案 B：本机浏览器 + PKCE

  1. CLI 启动 localhost 临时回调端口并生成 PKCE verifier。
  2. 打开浏览器完成登录。
  3. 授权码回到 localhost，CLI 用 verifier 换 token。
  4. 适合有桌面浏览器的开发机，但远程 SSH 体验较差。
PoC 推荐 Device Code CLI 不需要内置 client secret；短码只负责让用户确认设备，不能直接充当访问 token。 device_code 必须高熵、短期过期、一次性使用，轮询需要限速。

Token 优先保存到 macOS Keychain、Windows Credential Manager 或 Linux Secret Service。 无安全存储时才退回权限为 0600 的配置文件，并明确提示。服务器只存 refresh token 哈希， 支持 agent logout 与远程吊销设备。

充值流程

CLI 请求充值会话已登录 CLI 调用 POST /v1/billing/checkout，只提交服务端定义的套餐 ID。
服务器创建 pending 订单价格、币种、credit 数都从服务端配置读取，生成短期的一次性 Checkout URL。
用户在托管网页付款CLI 自动打开浏览器或打印 URL。支付卡号/支付凭证不经过 CLI 和你的 API。
支付平台调用 Webhook服务器对原始请求体验签、对事件 ID 去重，并核对订单、金额、币种及最终状态。
事务内到账订单从 pending 改为 paid，同时写一笔正数 credit 流水。CLI 轮询订单或再次执行 agent status。
CLI 显示“支付成功”不能触发到账 CLI、浏览器跳转页和 success URL 都可伪造。只有验签成功的服务端 Webhook 可以增加余额； 重复 Webhook 必须因为唯一事件 ID 而只处理一次。

一次 Agent run 的计费

CLI 生成 request_id一次用户动作对应一个 UUID；断线重试必须复用，避免重复消耗试用或余额。
Gateway 鉴权与限流从 token 得到 installation/user，限制输入大小、对话长度、并发、工具回合与单位时间调用量。
事务内预占匿名安装原子消耗 1 run；付费用户预占最大可能 credit。余额不足时不接触 LLM。
服务器调用 LLM服务器决定 provider、模型、系统提示词和 token 上限，并把 SSE/NDJSON 流转给 CLI。
结算成功后按实际用量或固定单价入账；确定未执行则释放预占；未知结果进入 reconciliation，不能盲目重复调用。

PoC 计价

每个顶层 agent run 扣 1 credit，并限制最多 N 个模型/工具回合。这最容易向用户解释。

以后计价

根据输入/输出 token、模型倍率和工具成本结算。先预占上限，收到实际 usage 后退回差额。

先定义“一个请求” 终端 Agent 的一次用户命令可能内部调用 LLM 多轮。建议“8 次”指 8 个顶层 run， 但每个 run 必须设置最大 LLM 回合、最大 token 和最大美元成本，否则一次免费 run 也可能很贵。

SQLite 最小数据模型

PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;

CREATE TABLE installations (
  id                TEXT PRIMARY KEY,
  token_hash        TEXT UNIQUE NOT NULL,
  public_key        TEXT,                   -- 可选：绑定本地密钥对
  used_trial_runs   INTEGER NOT NULL DEFAULT 0
                    CHECK (used_trial_runs BETWEEN 0 AND 8),
  risk_key          TEXT,
  user_id           TEXT REFERENCES users(id),
  created_at        TEXT NOT NULL,
  last_seen_at      TEXT NOT NULL
);

CREATE TABLE users (
  id                TEXT PRIMARY KEY,
  email             TEXT UNIQUE NOT NULL,
  status            TEXT NOT NULL DEFAULT 'active',
  created_at        TEXT NOT NULL
);

CREATE TABLE device_authorizations (
  device_code_hash  TEXT PRIMARY KEY,
  user_code_hash    TEXT UNIQUE NOT NULL,
  installation_id  TEXT NOT NULL REFERENCES installations(id),
  user_id           TEXT REFERENCES users(id),
  status            TEXT NOT NULL DEFAULT 'pending',
  expires_at        TEXT NOT NULL,
  approved_at       TEXT
);

CREATE TABLE refresh_tokens (
  id                TEXT PRIMARY KEY,
  token_hash        TEXT UNIQUE NOT NULL,
  user_id           TEXT NOT NULL REFERENCES users(id),
  installation_id  TEXT NOT NULL REFERENCES installations(id),
  expires_at        TEXT NOT NULL,
  revoked_at        TEXT
);

CREATE TABLE agent_runs (
  id                TEXT PRIMARY KEY,       -- 客户端 request_id / 幂等键
  subject_type      TEXT NOT NULL CHECK(subject_type IN ('installation','user')),
  subject_id        TEXT NOT NULL,
  status            TEXT NOT NULL,          -- reserved/running/succeeded/failed
  model             TEXT NOT NULL,
  input_tokens      INTEGER,
  output_tokens     INTEGER,
  reserved_units    INTEGER NOT NULL DEFAULT 0,
  charged_units     INTEGER NOT NULL DEFAULT 0,
  provider_req_id   TEXT,
  created_at        TEXT NOT NULL,
  completed_at      TEXT
);

CREATE TABLE payment_orders (
  id                  TEXT PRIMARY KEY,
  user_id             TEXT NOT NULL REFERENCES users(id),
  provider_payment_id TEXT UNIQUE,
  amount_minor        INTEGER NOT NULL CHECK(amount_minor > 0),
  currency            TEXT NOT NULL,
  credit_units        INTEGER NOT NULL CHECK(credit_units > 0),
  status              TEXT NOT NULL DEFAULT 'pending',
  created_at          TEXT NOT NULL,
  paid_at             TEXT
);

CREATE TABLE payment_events (
  provider            TEXT NOT NULL,
  provider_event_id   TEXT NOT NULL,
  received_at         TEXT NOT NULL,
  payload_hash        TEXT NOT NULL,
  PRIMARY KEY(provider, provider_event_id)
);

CREATE TABLE credit_ledger (
  id                TEXT PRIMARY KEY,
  user_id           TEXT NOT NULL REFERENCES users(id),
  delta_units       INTEGER NOT NULL,        -- 充值正数，消费负数
  reason            TEXT NOT NULL,
  reference_type    TEXT NOT NULL,
  reference_id      TEXT NOT NULL,
  created_at        TEXT NOT NULL,
  UNIQUE(reason, reference_type, reference_id)
);

匿名第 8/9 次并发必须原子处理

BEGIN IMMEDIATE;

-- 先 INSERT agent_runs；相同 id 冲突表示这是重试，绝不能再次计数
INSERT INTO agent_runs(id, subject_type, subject_id, status, model, created_at)
VALUES(:request_id, 'installation', :installation_id, 'reserved', :model, CURRENT_TIMESTAMP);

UPDATE installations
SET used_trial_runs = used_trial_runs + 1,
    last_seen_at = CURRENT_TIMESTAMP
WHERE id = :installation_id
  AND user_id IS NULL
  AND used_trial_runs < 8;

-- affected_rows 必须为 1，否则 ROLLBACK 并返回 TRIAL_EXHAUSTED
COMMIT;

金额用整数最小货币单位，credit 用整数。账本流水应不可变；纠错写反向流水，不直接修改历史。 PoC 只运行一个持有 SQLite 的服务实例，不要把 SQLite 文件放到网络文件系统供多机共享。

最小 API

接口调用方关键约束
POST /v1/installations首次运行的 CLI限速；返回一次性可见的 installation token，数据库只存哈希。
POST /v1/agent/runsCLIBearer token + Idempotency-Key；先预占再开始流。
GET /v1/agent/runs/:id断线恢复验证 run 属于当前 installation/user。
POST /v1/device/authorizeagent login返回 device_code、user_code、URL、过期时间和轮询间隔。
POST /v1/device/tokenCLI 轮询限速；批准后 code 只能换 token 一次。
POST /v1/token/refresh已登录 CLIrefresh token rotation；重用旧 token 时吊销 token family。
GET /v1/me/entitlementagent status显示试用/余额；真正 run 时仍要重新检查。
POST /v1/billing/checkoutagent billing只接套餐 ID；返回短期一次性 URL。
POST /v1/webhooks/payment支付平台原始 body 验签、事件去重、事务到账。

安全边界与常见坑

服务器 Secret

  • LLM Key、支付 Secret、token 签名密钥只放服务器环境变量/Secret Manager。
  • 为 Gateway 使用独立的低限额 LLM Key，设置日预算和异常告警。
  • 日志脱敏，不记录 Authorization header、完整提示词或本地文件 Secret。

CLI Token

  • access token 短期有效，refresh token 轮换并可撤销。
  • Token 泄露只影响该账户额度，不能暴露底层 LLM Key。
  • 支持 agent logout、设备列表和远程撤销。

成本控制

  • 限制单 run 的模型轮数、输入/输出 token、上下文大小、上传大小和超时。
  • 按 installation、user、IP 与全局设置速率及并发上限。
  • 服务器维护可用模型白名单，不能让 CLI 任意指定昂贵模型。

本地工具调用

  • 模型输出只是建议，CLI 应依据本地 policy 决定执行或要求确认。
  • 服务端计费权限与本地 shell 权限分离。
  • 工具结果控制大小，并在上传前过滤明显凭证和敏感文件。
流式协议建议 在发出第一个 SSE/NDJSON chunk 之前完成鉴权、幂等检查和额度预占。 流中使用明确事件：message.delta、tool.call、usage、 error、done。CLI 断线后用同一个 run ID 查询状态，不直接新建 run。

PoC 部署与验收

第一版可以是一台 VPS/容器：Caddy/Nginx 终止 TLS，单个 API 进程使用本地持久磁盘上的 SQLite WAL， 同一进程调用 LLM 和处理支付 Webhook。CLI 只需配置固定的 https://api.example.com。 一旦要多实例扩容，先将 SQLite 迁移到 PostgreSQL，再加入 Redis 限流和后台任务队列。

建议实施顺序

  1. 把现有 Agent 的 LLM 调用抽象为 provider，并实现一个 Gateway provider。
  2. 实现 installation token、8 次事务计数、幂等 run 和结构化流协议。
  3. 加入 Device Code 登录、token 安全存储、刷新、注销和设备吊销。
  4. 实现 credit ledger、固定充值包、托管支付页与 Webhook 幂等到账。
  5. 加入模型/回合/token/并发上限、成本告警、备份与恢复演练。

上线前测试

  • 解包 CLI 找不到任何 LLM Secret
  • 删除本地配置只会创建新安装，不会影响旧账
  • 并发第 8/9 次只有一次成功
  • 相同 request_id 不重复扣费
  • 断线恢复不会再调用一次 LLM
  • 伪造 Checkout 成功页不会到账
  • 重复 Webhook 只到账一次
  • device/user code 过期及重用均失败
  • refresh token 可轮换和远程吊销
  • 单 run 和全局成本都有硬上限
