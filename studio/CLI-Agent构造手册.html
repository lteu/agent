00

CLI Agent 到底是什么

定义

一句话：CLI Agent = 一个跑在终端里、能反复"思考 → 调用工具 → 观察结果"直到任务做完的程序，而不是一问一答的聊天框。区别不在"用了大模型"，而在有没有那个循环。

聊天机器人
输入 → 模型 → 输出文字

一次性、只能吐文字，看不见你的文件系统，也碰不了你的 shell。

≠
CLI Agent
输入 → ⟲ 模型 ⇄ 工具(读写文件/跑命令/搜索) ⟲ → 最终答案

活在你的文件系统和 shell 里，能循环很多轮，直到模型自己觉得任务完成。

AI Agent = Raw LLM Model + Agent Harness

模型只负责"生成文字"。Harness 负责让它在真实环境里可靠地跑完任务。

行业里有一句话说清了这件事：
"The model is commodity. The harness is moat." — Dr. Sarah Chen, Harness Engineering

换个比方：大模型是一匹力气很大的马，但它不知道方向、不知道边界、也不知道什么时候该停。Harness（马具）就是缰绳、马鞍和笼头——把原始能力引导成可控、有用的工作。Hugging Face 的 Phil Schmid 说得更直白：模型是 CPU，Harness 是操作系统——CPU 只管执行指令，内存管理、权限控制、错误恢复全靠 OS。没有 OS 的 CPU 只是个发热体；没有 Harness 的模型只是个 Demo。

01

所有 CLI Agent 的心脏：Agent Loop

核心原理

不管是几万行的 claudecode，还是几十行的最小实现，本质都是同一个循环：

①
发消息给模型
把「系统提示词 + 历史消息 + 可用工具清单」一起发给 LLM。
②
模型做判断
要么直接吐文本（任务结束），要么要求调用某个工具（继续）。
③
真正执行工具
在你的机器上跑这个函数（读文件 / 跑命令 / 搜索…），拿到结果。
④
结果塞回消息列表，回到①
模型在下一轮"看到"工具的执行结果，据此继续决策，直到不再要求工具，或触发轮次上限。

Agent Loop 电路图 — ①输入 ②模型判断 ③执行工具 ④结果回流，形成闭环

四个项目里真正对应这个循环的入口函数：

ccqueryLoop() · query.ts —— 一个 while(true) 的 async generator，每个 chunk 都 yield 出来，UI 增量渲染。
oc自己不写循环，委托给外部 SDK pi-agent-core，编排入口是 runEmbeddedPiAgent() · pi-embedded-runner/run.ts。
pirunLoop() · agent-loop.ts —— 外层 while 处理"用户中途追加消息"，内层 while 处理"还有没有工具调用"。
hsrun_conversation() · agent/conversation_loop.py —— while api_call_count < max_iterations（默认 90 轮）。

01B

Agent Harness：为什么 Demo 好用，生产就崩

概念补充

所有 CLI agent 都跑在同一个循环上，但"能跑的循环"和"生产环境里不崩的循环"之间，差的就是 Agent Harness——包裹着模型和循环的那层基础设施。这一层不是锦上添花，而是可靠性的来源。

36%20 步 × 每步 95%
可靠性数学就是这么残酷。假设 agent 每一步的成功率是 95%——听起来已经很靠谱了——但只要任务链条有 20 步，端到端成功率就会跌到 36%。这就是为什么团队总说"agent 95% 时间都好使"，但真实任务有三分之一会失败。

Harness 干的事，就是通过验证循环、重试策略、断点续跑，把这个复利式的失败率拉回可接受的水平。
Vercel 悖论：他们在做 v0 编码 agent 时发现，砍掉 80% 的工具，效果反而变好了。工具越多，模型越容易选错，错误越多，任务越失败。Harness 的工具编排层要做的不是"给模型更多选择"，而是根据任务阶段动态收窄可选范围——规划阶段不需要写文件权限，编码阶段不需要全网搜索。能力更少，可靠性更高。

Harness 不是 Framework：蓝图 vs 车间

两个词经常被混用，但说的不是一回事：

Agent Framework

构建时组件 · 蓝图和建材
  • 提供零件：提示词模板、工具抽象、内存接口、agent 循环
  • 帮你"把 agent 拼出来"
  • 面向开发者，关注设计与实现阶段
代表：LangChain / CrewAI / AutoGen

Agent Harness

运行时环境 · 工厂车间
  • 管执行：上下文怎么进、工具怎么验、失败了怎么办、什么时候叫人
  • 让 agent"在生产里跑得稳"
  • 面向基础设施，关注部署与运维阶段
代表：Claude Agent SDK / Codex Harness

实际项目里两者经常都用——用 Framework 搭骨架，用 Harness 管住运行。但很多团队跳过了 Harness 这一步，直接把 Framework 拼出来的 agent 扔去生产，那就是后面所有故障的起点。

一个有说服力的例子：同一个 Claude 模型，同时驱动着聊天界面、Claude Code 终端编码助手、企业 API 集成。权重完全一样，表现天差地别。差别就在 Harness——Claude Code 的 Harness 管文件系统、管终端会话、管验证循环、管跨会话状态；聊天界面的 Harness 只管对话历史和安全过滤。模型没变，周围的架构改变了一切。

02

把 Agent Loop 拆成六个可以单独理解的构件

拆解

循环本身只有几行，难的是"循环转起来不崩"所需要的周边系统。下面按你自己动手实现时会遇到的顺序，逐个拆解——每个都回答一个问题：这东西为什么存在？

01

循环引擎（Loop Engine）

所有智能都发生在"调模型"这一步，循环引擎本身很笨——它只负责"再问一次"。真正决定 agent 好不好用的，是这个循环要不要处理流式输出、要不要并行跑多个工具、要不要在中途允许用户插话。循环笨，周边不笨。

02

工具接口与注册表（Tool Registry）

LLM 不会真的"调用"任何东西——它只是吐出一段结构化文本（工具名 + 参数），是你的程序读懂这段文本、在注册表里找到对应函数、真正执行、再把结果写回对话。工具的 JSON Schema 就是喂给模型的"菜单"，菜单设计得好不好，直接决定模型点菜点不点得准。

03

系统提示词的动态拼装（System Prompt Assembly）

系统提示词不是一次写死、永远不变的字符串，它更像每轮现拼的三明治——层次越拆得清楚，越容易做提示词前缀缓存（prefix cache）省钱：

L1产品身份 / 工具使用规范（几乎不变，最利于缓存命中）
L2运行环境信息（cwd、git 状态、操作系统、当前时间）
L3项目 / 用户专属规则文件（CLAUDE.md / AGENTS.md / SOUL.md…）
L4记忆快照 / 本轮追加指令（最易变，放最后）
04

上下文压缩（Context Compaction）

对话开得越久，历史消息越多，而模型的上下文窗口是有限的。四个项目不约而同用了同一套分级策略，越往后成本越高、触发越少：

STAGE 1
截断/落盘超大工具输出
比如读了几万行的文件
→
STAGE 2
轻量合并 / 剪枝
去掉重复、过期的历史片段
→
STAGE 3
触发阈值 → 模型自我总结
用摘要替换原始历史
05

权限与审批（Permission Gate）

凡是会"动手"的工具（写文件、跑命令、发消息）都要过一道闸门：按规则直接判定，判不出来就弹出来问用户一句。这道闸门放在哪、松紧到什么程度，决定了 agent 是"放心用"还是"提心吊胆用"。典型判定顺序：

✕
命中黑名单规则
直接拒绝，不问模型也不问用户
?
命中"需询问"规则 / 工具自检未通过
弹窗给用户，等待 允许一次 / 本次会话 / 始终允许 / 拒绝
✓
命中白名单 / 只读安全操作
直接放行，无需打断用户

Harness 视角：六个构件，为什么缺了 Verification 不行

上面六个构件是从"自己动手实现时会遇到的顺序"来拆的。如果换一个角度——从 Agent Harness 的经典六组件框架（Context / Tools / State / Verification / Human-in-the-loop / Lifecycle）来对照，会发现上面的清单里少了一个最有杠杆效应的东西：

验证循环（Verification Loop）是所有 Harness 组件里投入产出比最高的一项——团队报告说加上结构化验证后，任务完成率从 83% 提到了 96%，模型没变，Harness 变了。

模式很简单：agent 产出结果 → 验证层按规则检查 → 通过就往下走，不通过就打回重试或升级。每次工具调用后验 schema、写代码后跑测试、发消息前查格式——这些静默失败如果不在每一步拦住，就会在多步执行后复利式地放大。

两套框架的对应关系：

Harness 经典六组件 对应本册构件 一句话解释
1. Context Engineering
上下文工程		 构件 03 + 04
系统提示词 + 上下文压缩		 决定模型每一步"看到什么"——不只是提示词，还包括检索文档、历史消息、工具输出、环境状态的全链路管理。核心矛盾是上下文窗口有限，得主动决定留什么、总结什么、丢什么。
2. Tool Orchestration

3. State & Memory

上下文压缩 + 跨会话		 跑几分钟甚至几小时的 agent 需要持久化状态 + 断点续跑——崩溃了能从上次检查点恢复，而不是从头再来。跨会话记忆（progress file、会话笔记）也属于这一层。
4. Verification & Safety
验证与安全 新增		 — 本册未单列 —
散见于权限/钩子		 单步 ROI 最高的 Harness 组件。每次工具调用后验证输出 schema、写代码后跑测试、提交前过 linter——把静默失败拦在每一步，不让错误复利累积。OpenAI Codex Harness 靠闭环验证跑出了 100 万行 agent 生成的代码。
5. Human-in-the-Loop
人机协同		 构件 05
权限与审批		 高风险操作（删数据、发消息、动钱、改基础设施）要过审批闸门。关键是校准：闸门太多不如手动做，太少等于裸奔。好的 Harness 从紧开始，随着对 agent 的信心建立逐步放松。

进阶能力		 生产级 agent 不是请求-响应函数，是长跑进程——需要健康检查（是不是卡循环了？）、资源限制（最大 token/最大时长）、优雅停机（存状态、放资源）、崩溃恢复（检测失败 → 读检查点 → 退避重试）。

长跑 agent 最隐蔽的失败模式：跨多轮多会话后，上下文逐渐堆满噪音、过期工具输出、已解决的错误、被推翻的决策——模型慢慢分不清什么是当前的、什么是重要的，就像一个连续加班的工程师还在干活，但已经不在状态了。Anthropic 的解法是双 agent 模式：每次会话启动时用一个"初始化 agent"重新整理上下文（相当于医院交接班），而不是把昨天的聊天记录原样塞回去。

04

怎么让它变成一条能敲的命令：运行时、终端渲染与进程控制

落地

前面讲的都是"脑子"——循环怎么转、工具怎么调。但你在终端里敲下 pi / openclaw 这几个字母时，背后还有三层容易被忽略的东西：谁把它注册成一条命令、谁把它画到你的屏幕上，以及谁来真正执行你敲的那条 shell 命令。

运行时与分发：Node + npm（以及 Python 那条平行线）

claudecode / openclaw / pi 三个都是 TypeScript 项目，跑在 Node.js 上；把它们变成一条全局命令，靠的都是 package.json 里的 "bin" 字段——告诉 npm："装的时候，在 PATH 里放一个叫这个名字的可执行文件，指向这个入口脚本"。npm install -g 之后，敲命令名其实就是在跑 node 入口文件.js。hermes-agent 是 Python，走的是同一件事的另一套实现：pyproject.toml 里的 [project.scripts] 把命令名映射到 Python 函数，pip install 之后同样注册进 PATH。殊途同归——都是"把一个函数入口，注册成 shell 里的一个名字"。

项目运行时命令怎么注册的
claudecodeNode.js（从周边依赖 react-reconciler / lodash-es 等推断）npm 全局安装注册 bin（本仓库是反编译源码，未附带 package.json）
openclawNode.js ≥ 22.16.0"bin": {"openclaw": "openclaw.mjs"}
piNode.js ≥ 22.19.0"bin": {"pi": "dist/cli.js"}（coding-agent 包）
hermes-agentPython[project.scripts] → hermes / hermes-agent / hermes-acp 三个命令

终端渲染层：TUI

Agent Loop 决定"想说什么"，TUI（Terminal UI）决定"怎么画到你的屏幕上"——这是两个完全独立的关注点，很多教程会把它们混在一起讲，容易让人误以为"循环"本身很复杂。

最简单：直接 print

流式 token 直接 stdout.write，工具结果原样打印。几行代码能跑，但没有多行编辑框、没有实时刷新、长输出会刷屏。

→
生产级：差分渲染引擎

把终端当成一块屏幕，维护一棵组件树，每帧只重绘"变化的部分"，配合终端同步输出协议做到不闪烁。

cc自研了一套类似 Ink（React for CLI）的引擎——ink.tsx / ink.ts，用 react-reconciler + 自研 Yoga 布局把组件树差分渲染到终端字符网格，支持同步刷新和 Kitty 键盘协议。
pi把 TUI 拆成独立发布的包 @earendil-works/pi-tui——差分渲染 + CSI 2026 同步输出（不闪烁），内置 Editor / Markdown / SelectList 等组件，支持在 Kitty / iTerm2 协议终端里内联渲染图片。
hs用 Python 的 prompt_toolkit 做交互式 CLI——审批弹窗、多行编辑器都靠它，实现不同但目标一样：让终端"能编辑、能刷新、不难看"。
oc更偏"消息"形态——大多数交互通过 Gateway 推给 Telegram / Slack / 微信等外部 IM 客户端渲染，本地并不强求一个富交互终端 UI。
一句话：TUI 花的功夫和"好不好用"强相关，但和"能不能跑"无关——最小实现里 print 就够了，差分渲染引擎是规模大了之后解决"闪烁 / 编辑体验 / 长会话可读性"的加固项，跟上一节的压缩、权限是同一类东西：不是核心原理，是工程加固。

进程与信号控制：谁来真正"跑"这条命令

bash 工具的 execute() 函数体里，藏着三个最容易被最小实现忽略、但一上真实场景就会炸的问题：要不要开一个真终端（普通管道 vs 伪终端 PTY）、Ctrl+C 该打断谁（当前工具，还是整个 agent 进程），以及命令派生出的子子孙孙进程谁来收尸。

项目怎么执行命令中断 / 清理机制
claudecode维持一个常驻的"影子 shell"会话（ShellSnapshot），cwd / 环境变量跨多次工具调用保留，更像你自己连续敲命令AbortController 把中断精确路由到当前这次 bash 调用（result.interrupted），不影响整个循环
openclaw默认走真伪终端（@lydell/node-pty），环境不支持时自动降级为普通 child_processkillProcessTree() 连带清理整棵子孙进程树，避免孤儿进程占着端口不放
piNode child_process.spawn()，一次性子进程，无 PTY监听 AbortSignal 的 abort 事件，触发后 kill 子进程
hermes-agent把决定权交给模型：工具参数 pty=true 时才开伪终端；执行地点还可能是 docker/ssh/daytona 等远程环境，不一定在本机process_registry.py 登记后台进程，滚动输出缓冲 + 崩溃后靠 JSON checkpoint 恢复
hs把"要不要 PTY"这个工程约束直接写进了工具描述里给模型看："Do NOT use vim/nano/interactive tools without pty=true — they hang without a pseudo-terminal." ——不是代码里悄悄兜底，而是教模型自己判断。
ockillProcessTree() 处理的是一个很常见的坑：一条 npm run dev 会在背后拉起好几个 watcher 子进程，只 kill 直接子进程的话，这些孙进程会变成孤儿继续跑。
为什么值得单独拎出来：很多最小实现直接用一句 os.system()/exec() 糊弄过去，平时看不出问题——直到模型跑出一条需要交互输入的命令（vim、密码提示、git rebase -i）卡死不动，或者用户按 Ctrl+C 把整个 agent 干掉、丢了正在进行的对话，才发现这层地基没打好。

05

最小可行 Agent：不到 60 行

动手

抛开工程细节，一个"能跑"的 CLI agent 用不了多少代码。对照着看，六个构件里真正躲不掉的只有①循环 ②工具表 ③LLM 调用三件——其余都是"规模大了以后不得不加"的加固。

# 伪代码：一个能跑的最小 CLI agent

TOOLS = {
    "read_file": {"schema": {...}, "run": read_file},
    "bash":      {"schema": {...}, "run": run_bash},
}

def agent_loop(user_input, system_prompt):
    messages = [{"role": "user", "content": user_input}]

    for turn in range(MAX_TURNS):
        response = llm.call(
            system=system_prompt,
            messages=messages,
            tools=[t["schema"] for t in TOOLS.values()],
        )
        messages.append(response.to_message())

        if not response.tool_calls:
            return response.text          # ① 模型直接回答 → 循环结束

        for call in response.tool_calls:  # ② 一次可能要求多个工具
            tool = TOOLS[call.name]
            if is_dangerous(call) and not ask_user_permission(call):
                result = "denied by user"
            else:
                result = tool["run"](**call.arguments)
            messages.append(tool_result_message(call.id, result))
        # ③ 结果已塞回 messages，回到循环顶部，让模型"看到"结果

    return "达到最大轮次，任务未完成"
①结束条件只有一个：模型这一轮没有要求任何工具调用。
②一次响应里可能带多个工具调用（比如同时读两个文件），要循环处理，别只取第一个。
③整个 agent 没有"隐藏状态"——messages 这个列表本身就是全部状态，模型的"记忆"就是把它整段重新发一遍。
把这 60 行放进生产，你需要：上下文超限时压缩（04）、危险操作弹窗确认（05）、流式展示进度、工具执行沙箱化——这正是上一节六大构件存在的原因，而不是额外的"炫技"。

06

从 MVP 到生产级：加固清单

清单

Harness 不是一口气堆出来的，是跟着 agent 的失败模式长出来的。业界的典型路径是四个阶段——从最高回报率的验证循环开始，按需往下加：

PHASE 01
验证循环
在不可逆动作前加一道检查——跑测试、验 schema、第二模型复核。单位工程小时可靠性提升最高。
PHASE 02
状态持久化
每步成功后写检查点。崩溃了从断点续跑，不用重来。故障时 token 成本省 30–50%。
PHASE 03
可观测性
每次工具调用/模型调用/决策点都打 trace。看板看完成率、失败模式、成本趋势。别等用户投诉才发现问题。
PHASE 04
人机协同闸门
破坏性/对外/昂贵操作走审批。从紧开始，对具体类别建立信心后逐步放松。生产安全网。
一个重要提醒：Martin Fowler 团队有记录——Harness 的工程量通常比 agent 逻辑本身还大。生产级 Harness 以月计，不是天计。排期的时候留够预算。

按"什么时候会痛"来排序，痛了再加，不必一开始就全都做。

对话开长了会报错 / 变慢 → 加上下文压缩
先截断超大工具输出，再轻量剪枝，最后才用模型自我总结（构件 04）。
敢让它碰真实文件系统 / 生产环境 → 加权限闸门
写操作、删除、执行命令都要过一道 允许/询问/拒绝（构件 05）。
用户等得着急 → 加流式输出
把 LLM 的 token 和工具执行进度实时吐给终端，而不是等全部跑完再显示。
一次任务要读/搜很多文件 → 加并行工具执行
只读、无副作用的工具可以并发跑；有副作用的（写文件）必须串行。
任务太复杂，一个循环装不下 → 加子代理
把子任务委派给一个新的、独立上下文的 agent 循环，做完汇报结果（如 Task / sessions_spawn）。
要在多用户 / CI / 不受信输入下跑 → 加沙箱
工具执行换成容器/远程执行后端，而不是直接跑在宿主机上。
想换模型，或想接入 IM → 加 provider 抽象层 + 消息网关
把"调用哪个模型""从哪个渠道收发消息"从核心循环里剥离出去。
想让同事 npm install -g / pip install 就能用 → 配好 bin / [project.scripts]
这是"脚本"和"命令行工具"的分界线（见 04 · 落地）——本地能跑不等于能分发。
长会话刷屏、编辑体验差 → 换成差分渲染 TUI
从 print 升级成组件化、只重绘变化部分的终端渲染引擎（见 04 · 落地）。

几处最值得拎出来讲的细节：

oc流式 tool_call 解析这个问题在它自己的代码库里其实没被解决——被"外包"给了看不到源码的外部 SDK；但在提示注入防御、循环检测、执行审批分级这几项上，反而是四家里做得最系统化、最像"安全产品"的，体现了它"编排层很厚、执行层很薄"的定位。
piSECURITY.md 原话："AGENTS.md 或注释里的指令可以轻易对 agent 做提示注入，这个没法防"，并把提示注入和沙箱缺失列为 Out of Scope——是态度选择（轻量工具，信任你的运行环境），不是遗漏。同样没有循环检测、任务规划工具、成本预算上限。
hs笔记里点名的"IterationBudget，子代理不占用父级步数"在源码里得到精确验证：父 agent 默认 90 轮，每个子代理独立 50 轮，二者互不相扣，总迭代数之和可以超过父级上限。
共同没有一家能安全地打断正在执行中的单个动作（都只能挡下"下一个"动作），也没有一家做到超长输入的自动化分块编排——都停留在"手动分页/搜索原语，交给模型自己调度"的水平。
总体观察
①同一问题在不同代码库里常收敛到相似的技术模式——压缩防丢信息普遍是"提示词强制指令+结构化路径提取"组合，流式 JSON 组装普遍是"delta 只拼字符串，block-stop 后才 parse"，说明这些不是某家的独创设计，而是这类问题的"标准解"。
②claudecode 和 hermes-agent 覆盖面最全，共同点是都把安全/可靠性当作核心产品功能在做，而不是外围加固。
③openclaw 不是从零写 agent loop 的项目，核心执行机制依赖外部 SDK，导致底层问题（流式解析、并发调度）表现较弱，但上层策略（安全、审批、子代理限流）做得最像产品。
④pi 是四家里最"轻量工具"取向的——多 provider 抽象层很扎实，但循环检测、任务规划、成本预算、破坏性操作确认、提示注入防御全部缺失，且是主动选择而非疏漏。
⑤四家共同的技术空白：中断正在执行的单个动作、超长输入的自动化分块——这两项可以作为后续自研的重点方向。
