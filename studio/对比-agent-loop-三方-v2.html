Agent Loop 四方对比 v2 · 新增 hermes-agent

同一个「模型 ↔ 工具反复交互」内核——但 ai 这轮把 v1 标记的「可借鉴项」真的实现了：流式调用、流式并发工具、上下文压缩、一整套 IDE 级工具。本次再补上第四方 hermes-agent：一个真实生产级的多渠道个人助理框架，循环体量比 Claude Code 还大一圈。

v1 → v2：ai 这轮补上了什么

v1 的结论是「ai 把循环还原成最朴素的样子，并按性价比挑 ①②④⑤ 来抄」。v2 已落地其中四项——而且没有牺牲可读性：循环主体仍是一个 for 生成器，只是从 85 行长到 178 行。

① 模型调用：非流式 → 流式 llm.ts · streamCompletion

新写的 streamCompletion 边收 SSE 边产出：content 片段实时吐 delta；并且能解析 tool_calls 的增量，在某个工具参数刚拼完整时立刻把它作为一次工具调用产出（依据「出现更大的 tool index」或「流结束」判定）。

③ 工具执行：顺序 await → 流式并发 engine.ts · StreamingToolExecutor

拿到一个工具调用就 add() 立即开跑（不 await），把 Promise 记下；本轮流结束后 drain() 按提交顺序回收结果。效果 = 模型还在吐后续 token / 后续工具调用时，先到的工具已经在并发执行——这正是 Claude Code 的 StreamingToolExecutor 思路。

② 上下文压缩：只会丢最旧 → 模型总结式 autocompact agent/compact.ts

每轮开头 compactInPlace：估算 token 超阈值（默认 40k）时，调一次模型把较旧那段历史总结成一条摘要，就地 splice 替换，只完整保留 system 与最近若干条；cut 对齐到 user 边界，绝不拆散 assistant(tool_calls) 与其 tool 结果。压缩失败静默回退，不影响主流程。

⑤ 内置工具：6 个 → IDE 级一整套 tools.ts

新增 edit_file(精确替换) · glob · grep · web_fetch · run_agent(子 agent)，与原有 write/read/list/bash/email/stock 合并，凑齐了 Bash/Edit/Read/Write/Glob/Grep/Agent/Web 这条 Claude Code 同款主线。

仍未补（且有意不补）： 模型回退（单 provider，失败即抛）、逐工具权限闸（场景是单可信用户，系统提示直言「你有权限」）、多 provider 抽象层。 这几项是为「无人值守 / 多模型 / 严格权限」付的税，ai 的场景用不上——继续留白以保住可读性。

新增第四方：hermes-agent 什么来头

不是研究项目，是一个真跑生产流量的多渠道个人助理网关（微信 ilink、QQ、飞书、Discord…）。它的循环 run_conversation()（agent/conversation_loop.py:518）把 Claude Code 那类「循环即产品」的思路又往前推了一步：单个函数体 ~4770 行，比 Claude Code 的 ~1730 行还大近 3 倍——因为多 provider 的报错分支、重试防护、压缩、终止判定全部摊平写在同一个函数里，几乎没有拆到外部编排层。

循环外形

外层不是 while True 而是 while (api_call_count < max_iterations and budget.remaining > 0) or grace_call（conversation_loop.py:633），内层还嵌一个「单次 API 调用重试」while retry_count < max_retries（:1093，默认 3 次，各种一次性恢复闸挂在 TurnRetryState 上，turn_retry_state.py:33）。全程无 yield/async def，是同步函数 + 线程池，不是生成器。

工具并发≠流式并发

模型调用始终走流式（conversation_loop.py:1289 起注释：「即使无消费者也优先流式，为了 90s 卡流检测」），tool_calls 增量也确实边流边拼（chat_completion_helpers.py:2093）。但工具要等整条流结束、拼完整个响应之后才按静态启发式规则决定顺序执行还是丢进 ThreadPoolExecutor 并发（tool_dispatch_helpers.py:104）——这是 Pi 那一档「流后并发」，不是 CC/ai 的「边流边跑」。

容错覆盖面最广

13 种终止原因、错误分类枚举近 20 种 FailoverReason（error_classifier.py:24）、双重模型回退（跨 provider 回退链 + 同 provider 多凭证池轮换，chat_completion_helpers.py:1172 / credential_pool.py:508）、五步压缩算法（含增量摘要迭代）、真插件钩子系统（pre_tool_call/post_tool_call/pre_verify… 近 20 个 hook 点）+ MCP 客户端 + 子 agent 委派（深度上限 1）。容错深度上，四家里它最厚。

但代价也最直白。 一个 4770 行的函数体意味着「一眼读懂」彻底放弃——这是 hermes-agent 用「单函数超大」换「所有状态就地可见、不用跨文件追」的取舍，和 ai 用「几十行一招」换「可读性」正好是两个相反方向的极端；Claude Code 与 OpenClaw/Pi 则各自把复杂度拆到了「同一循环里的分层调用」与「双层循环+外部编排壳」。

一句话结论（v2）

Claude Code

把循环本身做成产品。

一个 while(true) 生成器里塞进了全部上下文工程与容错：多级压缩、模型回退、流式工具并发、对超长/超 token 的逐级恢复。终止有七八种 reason。

OpenClaw

自己不写循环，而是包住 Pi 的循环。

真正的「模型↔工具」迭代交给内嵌引擎 Pi（earendil-works/pi）——一个 双层 while + steering/follow-up 的循环；run.ts 是它外面的调度壳：会话队列、密钥轮换、模型回退、溢出补偿、多聊天渠道。

ai（v2）

朴素循环 + 三样关键升级，仍一眼读懂。

同一个 for (step<25) 生成器，现在每轮：压缩历史 → 流式调模型 → 工具边流边并发跑 → 按序回灌。把 Claude Code 最值钱的三招（流式 / 流式并发 / 压缩）摘了过来，省下其余 1500 行的税。

hermes-agent

把循环做成产品的容错，全摊平进一个函数。

不是生成器而是一个 ~4770 行同步函数：外层 while + 内层「单次调用重试」while 双层嵌套，双重模型回退（跨 provider 链 + 同 provider 凭证池）、五步压缩、13 种终止原因、真插件钩子 + MCP + 子 agent 委派。工具执行是流后启发式并发（ThreadPoolExecutor），不是边流边跑。

同源，差距缩小又重新拉开。 四者内核仍完全一致——发消息 → 模型要么回话要么调工具 → 执行工具 → 结果塞回 → 再发。 v1 里 ai 与 Claude Code 的差距在「流式 / 并发 / 压缩」三处最扎眼；v2 后这三处已对齐机制（只是层数更少、没有逐级恢复闸）。剩余差距主要是容错深度（模型回退、超长恢复、权限）——而 hermes-agent 的加入说明这个「容错深度」维度上限还能更高：它的错误分类、双重回退、终止原因数量甚至超过 Claude Code，只是全部塞进单一函数而非分层拆出。

for (let step = 0; step < maxSteps; step++) {            // 默认 25 步封顶
  await compactInPlace(history, deps)                  // ① 超阈值→模型总结式压缩（就地 splice，保留 system+近况）

  const exec = new StreamingToolExecutor(execTool)     // 拿到工具就立即开跑的执行器
  let completion
  try {
    const stream = streamCompletion(history, { tools }) // ② 流式：content + tool_calls 都是增量
    for await (const part of stream) {
      if (part.type === 'text') yield { type:'delta', content: part.delta }  // 文本边流边出
      else { yield { type:'tool', … }; exec.add(part.call) }            // ③ 参数一拼完整就并发开跑
    }
    completion = stream.return                       // { content, toolCalls, finishReason }
  } catch (e) {                                     // ④ 被动恢复：上下文超长
    if (isContextOverflow(e) && !reactiveTried) { reactiveTried=true; await compactInPlace(history,deps,{force:true}); continue }
    throw e                                          // 不可恢复（含用户 abort）→ 抛给上层反馈
  }
  const { content, toolCalls, finishReason } = completion
  history.push({ role:'assistant', content, tool_calls: toolCalls })

  if (exec.size) {                                   // 有工具 → 回收并发结果，按序回灌，继续下一轮
    for await (const { call, result } of exec.drain())
      history.push({ role:'tool', tool_call_id: call.id, content: result })
    continue
  }
  if (finishReason === 'length' && outputRecovery<3) { // ⑤ 输出被截断 → 注入续写提示再来一轮
    outputRecovery++; history.push({ role:'user', content:'（系统）从断点继续，别重复别道歉' }); continue
  }
  return                                            // ← 无工具且未被截断 = 最终答复，结束
}

hermes-agent 是第四种形状：单函数里的双层 while。 它和 Pi 一样「工具并发发生在流结束后」，但判断并发与否的依据不是 Pi 的「配置开关」，而是逐批启发式（tool_dispatch_helpers.py:104）：只读工具白名单 + 路径不重叠才并发，写/patch 混批一律顺序——这是四家里唯一对「能不能并发」做逐次动态判定而非静态策略的。同时它是唯一同时具备跨 provider 回退链与同 provider 多凭证池轮换两层模型容错的（CC/OC 各有一条回退链，ai 无回退）。
v2 后的对位关系。 ai 的 compactInPlace ≈ CC 的 autocompact（仅这一层，没有 budget/snip/micro/collapse 那四层前置裁剪）； ai 的 StreamingToolExecutor ≈ CC 的 streamingToolExecutor.addTool（机制相同，但 ai 无 canUseTool 权限闸、无 withhold 恢复）。 内核招式对齐，容错深度仍是 CC 厚得多——但 hermes-agent 的压缩五步算法、双重模型回退、~20 种错误分类，容错深度比 CC 还要更进一层，只是没有拆出「五级压缩」那样清晰的分层命名。

给 ai 的最小补法。 不必抄 CC 的五层闸或 OC 的自适应分页，单是给 read_file 加一对 offset/limit（行号）参数 + 默认只读前 N 行，就能让模型对大文件「先扫一段、要哪段读哪段」，而不是吃一个头部 20000 字的死截断后无路可走—— 几行改动，契合 ai「几十行就对齐一招」的一贯取舍。再进一步可仿 CC 的 stat 预检，避免把几 MB 文件整个 readFileSync 进内存。 hermes-agent 的 read_file 正好就是这个「最小补法」的成品实现——读前算 total_lines、超预算按整行截断并直接把 next_offset 写进提示里，可以直接当参考实现抄。

hermes-agent 独有：「自我学习循环」宣称的事实核查

这项能力在 CC / OpenClaw / ai 三家里都不存在，逐维度表里只能打「无」，所以单独拉出来核实。官方原话大意是：「唯一自带学习循环的 agent——从经验中创建技能、在使用中改进它们、自我提醒沉淀知识、检索自己的历史对话、并跨会话构建一个不断加深的用户模型」。逐条对照源码后：自动触发的部分是真的、且默认开启；但「学习」本身每次都是一次 LLM 自我判断，不是可验证的确定性流程，且「用户模型」有硬字符上限。

宣称 实际机制 判定
① 从经验创建技能 每 10 次工具调用自动 fork 一个后台子 agent（turn_finalizer.py → background_review.py），塞给它一段写死的 prompt，要求「主动判断是否该新建一个技能」并调用 skill_manage(action="create")。触发是代码保证的；但决定「值不值得存」全靠这个子 agent 的判断，没有任何确定性抽取算法 部分兑现
② 使用中改进技能 同一后台 review 会顺带提示「如果某个技能这轮被证明错了/漏了步骤，立刻 patch」；skill_usage.py 只记录 view/use/patch 次数，不记录成功/失败——「改进」= LLM 自我报告，没有效果反馈信号驱动。更严格的合并/清理通道 curator.py 默认关闭 部分兑现
③ 自我提醒沉淀知识 四家里唯一有代码强制的「提醒」：记忆每 10 用户轮、技能每 10 工具轮各自独立计数，到点强制跑一段有限步数（≤16 步）的子对话，模型必须回应。但两份 review prompt 都明确允许「无需保存，直接结束」——是强制「考虑」，不是强制「写入」 兑现（按设计）
④ 检索自己的历史对话 session_search 是 SQLite FTS5 关键词全文检索，不是语义/向量召回；且是纯「模型主动调用」的工具，没有任何地方自动触发它——模型不问，它就不会自己去翻旧对话 兑现但夸大
⑤ 跨会话加深用户模型 真实机制是 USER.md，经 memory 工具写入，由 ③ 的记忆提醒周期性触发更新；但硬编码上限 1375 字符，且只在会话开始时整体注入一次（冻结快照），旧内容会被覆盖/精简而非无限累积。名字最像「负责这个」的 curator.py 其实只管技能维护，和用户模型完全无关（这是宣称与代码差距最大的一处误导） 部分兑现
最容易被误读的一点：curator ≠ 用户建模。 curator.py 的文档字符串明确写着它是「定期审查 agent 创建的技能」的辅助模型任务——全部逻辑都是技能生命周期管理（陈旧下线/归档/合并），且默认每 7 天空闲触发一次，完全不碰 USER.md/MEMORY.md。真正承载「用户模型」的只是一份 1375 字符上限、由 memory 工具写入的静态文件。
整体判断。 支撑「自我学习」说法的基础设施是真的、且四家独此一份：background_review.py 这个「按代码定的周期强制 fork 子 agent」机制，是唯一让「创建/改进技能」「沉淀知识」脱离「纯粹指望模型自觉」的部分。但把它读成「agent 会自己变得更懂你」需要打折扣——本质仍是「每隔 N 轮，强制问一次 LLM 要不要记点什么」，技能这侧没有效果反馈闭环，用户模型这侧有硬字符上限。工程是真的，但比宣传语克制得多。

v2 之后，ai 还剩哪些可选项

v1 清单里的 ①②③⑤ 已落地（流式 / 压缩 / 并发 / 工具集）。本轮又补了 Claude Code 的两道恢复闸：输出截断续写（对标 max_output_tokens_recovery）、上下文超长强制压缩重试（对标 reactive_compact_retry），以及用户主动中断（Esc / IM 发「停」）。剩下按性价比：

改进点现状可借鉴谁 · 怎么做
④ 模型回退 单一 provider，请求失败直接抛错（流式与非流式都是） OC 的回退链：主模型 5xx/限流时自动切备用 baseURL/model，对多 provider 配置天然契合。流式下需处理「已吐一半再切」的清理。
⑥ 会话串行 QQ/微信已用 busy 集挡住同会话并发；但仅「拒绝」而非「排队」 OC 的 lane 队列：给每个 session 一把串行锁排队执行，而非直接回「上一条还在处理中」。
＋ 工具结果总预算 单个结果截到 20000 字符；多个大结果叠加仍可能偏大（压缩会兜底但偏被动） CC 的 applyToolResultBudget 或 hermes 的「单结果 10 万 + 单轮聚合 20 万字符」双上限：对「聚合后」的工具结果设总预算，比逐个截断更稳。
＋ read_file 分页续读 头部截断死路一条，模型拿不到后半段 hermes 的 read_file(offset,limit)：读前先算行数判断是否会截断，截断时把 next_offset 写进提示，模型可自主续读——比照抄 CC 的五层闸成本低得多。
＋ 只读工具真并发收益验证 StreamingToolExecutor 已并发；但若 provider 把 tool_calls 一次性吐出，并发收益取决于工具自身耗时 对 read_file/glob/grep/web_fetch 这类无副作用、可能慢的只读工具，并发收益最大——已天然受益于现机制。
取舍没变，只是天平更靠中间了。 ai 依然不打算抄 Claude Code 那 1730 行的全部容错； 但 v2 证明：流式、流式并发、总结式压缩这三招，各自只要几十行就能落进一个仍然「一眼读懂」的循环里。剩下的 ④⑥ 属于「多 provider / 多并发会话」才需要的税，按需再加。
