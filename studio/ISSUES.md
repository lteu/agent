# 上下文管理类
- 压缩会丢关键信息——总结旧历史时，UUID、文件路径、用户明确说过的约束这些"面目相似但语义关键"的东西容易被模型总结掉。hermes-agent 专门做了 identifier-preservation 策略来防这个。
- 工具调用参数流式拼接的完整性——边流边解析 tool_calls 的 JSON 增量时，参数没拼完就被误判"结束"会导致调用失败或参数残缺。
- 超长输入。如果agent的任务是读一本1000页的书怎么办？如果，需要在上万行的代码中，找bug怎么办？
- long horizon task 怎么处理？
- 信息复用。agent在理解万行代码库的项目的基础上，成功的加了一个功能。再添加新功能时，能否复用之前的信息，还是需要从头了解代码库。同一个session下，能否理解。重启session后，怎么办？


# 执行可靠性类
- 并发写入竞态——多个工具并行跑时，如果两个都要写同一个文件/同一段状态，谁的结果算数？claudecode 靠 isConcurrencySafe 分只读/写操作，hermes-agent 靠"路径不重叠才并发"的启发式，本质都是在防这个。
- 循环卡死 / 重复无效调用——模型反复调同一个失败的工具，参数没变化，人类一看就知道要换思路，模型有时候就是绕不出来。openclaw 的 before-tool-call 钩子里专门做了循环检测。
- 中断的一致性——用户 Ctrl+C 打断时，如果工具已经写了一半文件，状态是脏的；打断粒度（当前工具 vs 整个循环）设计不好就会丢上下文或留下半成品。


# 安全类
- 提示注入（prompt injection）——工具读回来的内容（网页、邮件、文件）本身可能包含"伪装成指令"的文本，试图劫持 agent 后续行为。这个和"危险动作"不是一回事：危险动作是模型自己想干什么，注入是外部数据在操纵模型想干什么。你现在跟我对话的这个环境本身就有一套"边界"规则专门防这个。
- 权限疲劳——审批弹太多次，用户会无脑点"始终允许"，闸门形同虚设，这是个 UX 问题不是技术问题，但工程上要考虑怎么分级不同风险动作减少无效打扰。
- 如果用户输入有歧义，agent理解要删数据，删重要文件怎么办？


# 规模化类
- 多 provider 抽象的代价——不同厂商的 tool-calling 格式、流式协议、上下文窗口大小都不一样，抽象层做薄了功能受限，做厚了每加一个新模型都要适配。pi 和 hermes-agent 都为此单独抽出一层。
- 成本/预算失控——长任务 + 子代理递归调用，token 花销会指数级涨，需要预算硬顶（hermes-agent 的 IterationBudget，子代理不占用父级步数）。
